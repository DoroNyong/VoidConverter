# 1차 피드백 정리

게임 개발 프로그램 1:1 피드백을 기록하고, 현재 게임 상태에 맞춰 해석한 문서다.
**해석과 순서는 우리끼리 정리한 초안이며, 확정이 아닌 것은 "정할 것"에 따로 적었다.** 여기서 나온 아이디어는 [ideas.md](ideas.md)에도 상태 "아이디어"로 남긴다.

## 1. 피드백 원문

1. 효과가 발동한 칸은 좀 다르게 표현해서 뭐가 걸린지 알 수 있게 해라.
2. 유저들은 글을 읽지 않는 사람이 있다. 불특정 다수에게 배제 하게 되는 일을 최대한 없게끔 만들어라.
3. 배치할때 배치 타일에 직접적으로 확률을 표시하는게 좋을거같다.
4. 타일 배치 할때 활성화 되는 블럭이 시각적으로 보여주자. 선택 타일내에서 밝은 테두리가 돌아가게 하면 글로 설명하지 않아도 확률로 적용되는걸 직관적으로 보여줄 수 있다.
5. 게임 개발은 음식점이다. 키오스크나 음식 받는 곳, 반납하는 곳 배치에 따라 확 다르듯이 게임도 이런 점에서 유저들이 편하게 해야된다.
6. 심플하다. 하지만 심플해서 재미가 없을 수 있다. 항상 조심해야한다.

### 숙제 (다음 주까지)

- 게임다워졌으면 좋겠다.
- 밸런스는 지금 멈추고 기능 개발을 우선으로 하자.
- 웹빌드 해서 공유하기.

## 2. 현재 상태와 해야 할 일

| # | 피드백 | 현재 상태 | 해야 할 일 |
|---|---|---|---|
| 1 | 발동한 칸을 다르게 표시 | 발동한 칸(Used)과 덮이기만 한 칸(Covered)이 둘 다 어둡게 보인다. 덮인 칸에는 빨간 테두리만 붙는다. | 이번 배치에서 터진 칸을 따로 강조한다. 발동한 칸 / 덮여서 죽은 칸 / 살아 있는 칸이 한눈에 구분되게 한다. |
| 2 | 글을 읽지 않는 사람도 이해해야 함 | 규칙은 글과 숫자로 설명한다. | 규칙을 글이 아니라 보여 주는 방식으로 전달한다. |
| 3 | 배치 타일 위에 확률을 직접 표시 | 확률은 오른쪽 패널과 드래그 고스트 옆에 있다. | 덮이는 각 칸 위에 퍼센트를 올린다. |
| 4 | 활성화될 칸을 시각적으로 (밝은 테두리가 돌아감) | "덮은 칸 중 하나만 무작위로 터진다"를 글로 설명한다. | 덮인 칸들 사이를 밝은 테두리가 돌다가 한 칸에 멈추는 연출을 넣는다. |
| 5 | 음식점처럼 동선과 편의성 | 스냅 드래그는 이미 했다(2026-11-09). | 손·눈이 가는 길을 점검하고, 비어 있는 마름모 판 모서리에 UI를 배치한다. |
| 6 | 단순해서 재미없을 수 있다 | 규칙은 단순하다. | 단순함은 지키되 재미가 줄지 않는지 계속 확인한다. 판단 기준이 아직 없다. |

### 서로 이어지는 점

- **1, 3, 4번은 한 덩어리다.** 배치 전에 각 칸의 확률이 보이고(3), 어느 칸이 후보인지 테두리가 돌고(4), 터진 칸이 표시된다(1). 이 흐름이 2번(글 없이 규칙 전달)의 답이기도 하다.
- **4번 연출은 규칙 설명을 겸한다.** 테두리가 돌다가 한 칸에 멈추는 모습이 "하나만 무작위로 터진다"를 보여 준다.
- **5번은 UI 배치 문제다.** 마름모 판으로 바꾸면서 생긴 네 모서리가 HP, 골드, 손패, 확률 표시를 놓을 자리다.
- **6번은 "게임다워졌으면"과 이어진다.** 칸이 터지는 맛, 선택의 긴장감, 이미지와 이펙트.

## 3. 숙제별 메모

### 게임다워지기
- 위 시각 피드백(1, 3, 4번), 타일 이미지(마름모를 먼저 만든 이유), 이펙트.
- 이미 있는 것: 핵심 순간 타격 효과와 소리(v0.1.4), 마름모 판, 스냅 드래그.

### 밸런스 멈추고 기능 우선
- 기존 계획은 "아이템을 넣으면서 밸런스를 계속 조정"이었다. 이번 주는 **밸런스 조정을 빼고 기능만** 만든다.
- 수치(체력 6, 위습/브루트 구성 등)는 지금 값으로 둔다.

### 웹빌드로 공유
Unity WebGL 빌드가 필요하다. 미리 확인할 것:
- 소리를 코드로 만들어 내는 부분이 WebGL에서 되는지
- 드래그가 터치 입력에서도 되는지 (폰으로 여는 사람)
- 다양한 화면 비율에서 카메라 맞춤이 되는지
- 첫 로딩 시간

## 4. 정할 것 (아직 결정 아님)

- **이번 주 순서.** 제안: 시각 피드백(1, 3, 4번) → 웹빌드로 공유 가능한 상태 → 이미지·이펙트 → 아이템 기능. 웹빌드를 일찍 해야 다른 사람 눈으로 막힌 곳을 볼 수 있다는 이유다.
- **합격 기준.** "처음 하는 사람이 글 없이 첫 판에서 규칙을 알 수 있나"를 기준으로 삼을지.
- **6번의 판단 기준.** 재미가 줄지 않았는지를 어떻게 확인할지(예: 다른 사람 플레이 관찰).

## 5. 진행 기록

(작업이 끝날 때마다 날짜와 함께 여기에 적는다.)

### 2026-11-10 — 제출 일정과 결정

숙제와 함께 받은 공통 과제(목요일 11/12까지, 노션에 링크로 제출): 데모 v1(시작 → 플레이 → 끝, 성공·실패·재시작 포함), 그레이박스 → 아트 교체 1세트, 에셋 출처·라이선스 목록, 외부 테스터 플레이테스트, 역할 맵(1인: 역할 시간표), 주간 기록 #3. 완료 기준은 "안내 없이 처음부터 끝까지 플레이", 문제 목록에는 우선순위를 붙인다.

결정(개발자):
- **보스 이후:** 클리어 화면에 다시하기 버튼을 두고 루프시킨다. (이전의 "종료 또는 처음부터"가 이걸로 정해졌다.)
- **아트:** AI로 만든다. 직접 찾을 시간이 없다. 에셋 출처 목록에는 AI 생성이라는 점과 사용한 도구를 적는다.
- **테스터:** 외부 테스터는 없다. 개발자가 직접 플레이하고 관찰해서 문제 목록을 쓴다. 제출 문서에 이 사정을 그대로 적는다.

일정: 화(11/10) 끝 흐름 → 시각 피드백 3종, 수(11/11) 아트 교체 → 설치본 빌드 → 직접 플레이 관찰, 목(11/12) 문제 목록 → 치명적인 것만 수정 → 문서 → 제출. 웹빌드는 남는 시간에.

### 2026-11-10 — 끝 흐름 구현
- 타이틀 화면(Start 버튼, Space도 가능), 클리어 화면과 패배 화면(Play Again 버튼, Space도 가능)을 `FlowScreenView`로 추가했다. 장면 파일을 고치지 않고 `GameController`가 있는 장면에서 스스로 만들어진다.
- 클리어 화면에는 도달 단계, 골드, HP, 공격력/마법, 가진 아이템이 나온다. 패배는 마지막 타격을 볼 수 있게 1.2초 뒤에 나온다.
- 이전의 작은 Restart 버튼과 배너는 이 화면들에서 숨겼다(`RoundButtonView`, `HudView`).
- 확인: 플레이 모드에서 타이틀 → 시작 → 패배 → Play Again(HP, 아이템, 단계 초기화) → 클리어 화면을 코드로 상태를 바꿔 가며 봤다. 마우스로 버튼을 눌러 보는 것과 실제 보스까지 가서 클리어하는 것은 직접 해 봐야 한다.
